# 01 Brief — LeaveBot 請假系統

- 負責人：本組（D2 卡 A）
- 日期：2026-11-01
- 狀態：已確認（2026-11-01，小組於卡 K 確認）
- 審查者：本組成員；決策逾時由講師裁定

## 問題與證據

好日子科技的員工目前用訊息提出假單，送出後不知道是否登記成功，也無法自行查看自己的申請與狀態。

- 來源：課程題目 `course/01-上課/03-LEAVEBOT.md`「情境」。
- 待確認前提：題目沒有提供漏登、重複詢問或人資處理時間的實際數據，這些影響都**未量測**，由人事或講師提供後再補。

## 目標與成功判準

### G-01｜員工送出假單後立即確認已登記

- 怎麼判斷：選員工、填表、送出後，頁面顯示成功訊息，「我的假單」立即出現該筆，狀態為「待審核」（`pending`）。重新整理後資料仍在。
- 目前基準與目標：基準未量測。本次的代理證據是一條可重做的人工驗收操作，加上自動化 TC 結果。

### G-02｜不合法的申請被拒絕且不留下資料

- 怎麼判斷：缺必填、員工不存在、假別或時段不合法、結束早於開始、半天跨日、區間內沒有工作日、理由超過上限（100 字，D-07）時，後端拒絕並回傳可理解的錯誤。資料庫筆數不變。
- 目前基準與目標：基準未量測。目標是上述拒絕路徑都有代表 TC，並實際執行通過。

### G-03｜天數由系統一致計算

- 怎麼判斷：只計週一至週五，整天 1 天，上午或下午 0.5 天。客戶端送來的天數與狀態不被採用。
- 目前基準與目標：基準未量測。目標是以固定日期的 TC 獨立核算預期值，再與程式結果比對。

## 範圍與非目標

本次交付一條表單主線：員工從下拉選單選自己（不登入），填寫假別（`annual`、`personal`、`sick`）、開始日期、結束日期、時段（整天、上午、下午）與理由。後端驗證後存進 SQLite，新假單狀態固定為 `pending`。「我的假單」只列所選員工的申請。

| ID | 這次不做 | 理由與重看時機 |
|---|---|---|
| NG-01 | 登入與身分驗證 | 課程邊界，用下拉選單代替；正式導入前重看 |
| NG-02 | 主管核准或駁回（C1） | 延伸挑戰，主線驗收後另開票 |
| NG-03 | 特休額度、同組人數提醒（C2、C3） | 延伸挑戰，需要額外資料與規則 |
| NG-04 | 國定假日、附件 | 題目排除；天數只扣週末 |
| NG-05 | 自然語言解析與模型 API（C4、C5） | 主線不呼叫 LLM、不需要金鑰 |
| NG-06 | 重複或重疊假單的後端去重 | 小組決策 D-03；有誤登資料後再重看 |

## 限制、假設、風險與決策

- 限制：技術依 `course/01-上課/04-STACK.md` 固定，使用 FastAPI、原生 HTML/CSS/JS、sqlite3、pytest，只有單一 HTTP 服務，不開 CORS。時程是 D2 一天，教學規模為 AC ≤ 10、FR ≤ 10、TC 6–12。
- 假設：員工名單由系統預先提供，不在本次維護。請假規則僅供需求設計，正式採用前須由人事確認適用規定（來源：03-LEAVEBOT.md）。
- 風險：
  - 不去重時，網路慢或使用者重按可能產生重複假單。降低方式是送出期間停用按鈕，並接受這個殘餘風險（D-03）。
  - 理由是使用者文字，可能含 HTML 或指令。降低方式是只當文字保存，並以 `textContent` 呈現。
  - 日期計算錯誤會影響天數。降低方式是用固定日期與跨週末的 TC 獨立核算預期值。
- 待決：無阻塞核心流程的項目。「200 字」的計算方式（以字元計、是否先去除前後空白）留給卡 C 的 SRS 明定。

## 小組決策（2026-11-01 確認）

| ID | 問題 | 決定 | 影響 |
|---|---|---|---|
| D-01 | 理由是否必填、長度 | 選填，最多 200 字；超過由後端拒絕且不存檔。**長度部分已由 D-07 取代** | 一條拒絕路徑與 TC；空理由可成功送出 |
| D-07（2026-11-01 卡 J 變更） | 理由長度上限 | 改為最多 100 字；計算方式沿用 D-05；超過由後端拒絕且不存檔 | AC-02.5、FR-06、TC-08 修訂；票 002 |
| D-02 | 是否接受過去日期 | 接受；不以「今天」作為拒絕依據 | 主線驗證不依賴今天日期，可補登已休的假 |
| D-03 | 重複送出的回饋 | 後端不去重；前端在請求進行中停用送出按鈕，完成後解鎖並顯示結果 | 相同內容再次送出會新增一筆；按鈕鎖定由人工操作驗收 |
