## 範圍、風險與策略

最怕失敗的路徑是「送出後看起來成功，但資料或天數錯誤」，以及「拒絕時仍留下資料」。自動化以 API 驗收（`TestClient` 加暫存資料庫）為主，天數計算另做單元測試；按鈕鎖定、保留表單、畫面上的文字安全，只能靠人工操作確認。

- **天數算錯**（高）：員工額度與紀錄錯誤。以單元測試（TC-02）驗計算本身，以 API 測試（TC-01、06）驗接線，因為計算是純函式，邊界最便宜在單元層抓到。對應 FR-05。
- **拒絕仍寫入**（高）：資料庫出現不合法假單。每個拒絕 TC 都核對假單筆數不變（TC-04～08）。對應 FR-08。
- **客戶端指定狀態或天數**（高）：繞過規則。以 API 測試（TC-03）驗證，因為信任邊界就在 HTTP 層。對應 FR-07。
- **看到別人的假單**（高）：資料隔離失效。以 API 測試（TC-09）驗證。對應 FR-09。
- **理由被當成 HTML 執行、重啟後資料消失**（中）：API 測試（TC-11）驗證保存與 SQL 參數化；人工（TC-12）驗證畫面以文字顯示。對應 NFR-01、NFR-02。
- **按鈕鎖定、錯誤後保留表單**（中）：前端行為，以人工測試（TC-12）驗證。對應 FR-10、D-04、NFR-04。

**不測範圍**（缺口，若要納入請講師決定）：
- 資料庫故障回 `500 DB_ERROR`：需要模擬檔案無法寫入，課堂價值低。
- `INVALID_BODY`、`INVALID_REASON`：格式防呆，風險低。
- NFR-05 效能：沒有基準，待量測。
- `/api/health`：屬於票 000 的骨架檢查，不編 TC 號。
- 本次沒有 LLM 功能，不做模型 eval 或注入評測。

## 環境、資料與判定方式

- **執行**（repo 根目錄）：`.venv\Scripts\python.exe -m pytest`。macOS／Linux 用 `.venv/bin/python -m pytest`。
- **隔離資料庫**：每個測試用 pytest `tmp_path` 建立 `create_app(db_path=tmp_path / "test.db", now=固定時鐘)`，不讀寫 `backend/data/leavebot.db`（NFR-03）。
- **可重建資料**：`init_db` 自動寫入 E001 王小明、E002 李小華、E003 陳大同，沒有假單。
- **固定時鐘**：`now = lambda: datetime(2026, 10, 12, 1, 0, tzinfo=timezone.utc)`，只影響 `created_at`。主線規則不使用今天日期（D-02）。
- **判定方式**：
  - 預期值來自 SRS 決策表與下列人工算例，不呼叫 `count_days` 或其他實作函式來產生答案。
  - 拒絕案例同時核對 HTTP 狀態、`error.code`、`error.field`，以及假單筆數不變。
  - 筆數用 API-04 或直接查詢暫存資料庫取得。
- **日期參考**：2026-10-12 週一，10-16 週五，10-17、18 週末，10-19 週一，10-23 週五。
- **預設請求**（以下稱「基本請求」）：

  ```json
  {"employee_id": "E001", "leave_type": "annual", "start_date": "2026-10-12", "end_date": "2026-10-14", "period": "full"}
  ```

4. 預期：`200`，1 筆，內容同步驟 2。

| 移除 `employee_id` | `MISSING_FIELD` | `employee_id` |

| `leave_type = {"x": 1}`（物件，卡 I 回歸） | `INVALID_LEAVE_TYPE` | `leave_type` |

### TC-08｜理由長度邊界（AC-02.5、FR-06）

層級：API。理由以「假」字組成，每字計 1 個字元。

- ① 100 個「假」→ `201`，`reason` 長度 100。
- ② 101 個「假」→ `422 REASON_TOO_LONG`（`field=reason`），筆數不變。
- ③ `"   " + 100 個「假」+ "   "` → `201`，存下的 `reason` 為 100 個「假」，前後沒有空白。

**修訂紀錄（2026-11-01 卡 J，D-07）**：上限由 200 改為 100，計算方式不變。原 ① 200 字可送出、② 201 字拒絕、③ 前後空白加 200 字，依新規格改為上表。② 改用 101 字取代 201 字，作為「剛好超過上限」的邊界；201 字案例不再保留，以免重複。修訂依據：AC-02.5、FR-06、D-07，經小組於 2026-11-01 確認。② 必須先在舊實作（上限 200）跑出紅燈，再改程式。

執行方式：acceptance。v0.2 已於 2026-11-01 由票 002 執行通過。
